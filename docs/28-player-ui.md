# 28 — Player UI: the `ui` layer, widgets, layouts and fonts

The browser client in which a human plays the whole campaign: one page, `/play`, with a DOM-free `ui` layer (mouse
regions, buttons, bitmap text, cursors, popups and message boxes with the original's semantics) that emits a draw list,
a WebGL2 renderer that draws it and the tactical world at a logical resolution, and the original screens built on that
foundation. This doc covers the layer and the game page, the client's copy of the game, cursor hints, assets, scaling,
the widgets, fonts and layouts, the stub skin, the test harness and the UI's performance targets. Siblings: `30` the
screens; `29` every command, query, hint, view field and event a screen uses; `01` D10, D15, D16 and the layers; `04`
the drivers, view frames and the server side of the rule pack and assets; `05` the world renderer and its partial
redraws; `06` soldier presentation; `20` lighting; `27` client settings; `31` data versions, display languages, sound
and video; `32` the stub pack and the launcher. Original-source paths are relative to
`reference/stracciatella/src/game/` (`src/sgp/…` to `reference/stracciatella/`); each module's `@src` header names the
functions it ports.

## 2. Principles

**The original's look and behaviour is the default.** The original's screens are fixed compositions of STI and PCX
art, bitmap text in palette-index colours and mouse regions at constants from `#define` blocks; once the shared widgets
exist, rebuilding a screen is transcription. A part is **simplified** (a cheaper equivalent shows the same thing) when
the original mechanism cannot work in a browser (pointer warping, mouse confinement, OS key repeat), depends on the
frame rate (fades, zoom speeds), only spares a software renderer work (dirty rectangles, background save buffers) or
needs a server rule the client must not reimplement. A part is **left out** when it needs simulation that does not
exist or is costly flavour; each such part is a row of `deviations.md` or `gaps.md`.

**Rules from D15 and D16 that bind every screen:**
1. **No hand-written rule in the client.** Every number the simulation computes (costs, chances, ETAs, prices, what
   fits where, what is enabled) comes from the view, from a cursor hint (§4) or from a server query. A screen may
   restate an *enable* rule on view fields only when the rule is trivial and the command refuses anyway; the server
   validates every command on the full state.
2. **No hidden state.** A screen shows only what the original shows at that moment, and hints and queries run on the
   player-knowledge projection, where soldiers the player does not see do not exist. Where the original's own UI leaks
   hidden state (a menu line shaded because of enemies nobody has seen), the projection does not; the command then
   refuses with the original's message.
3. **Presentation never feeds the simulation.** Client timers (blinks, flashes, lip sync, fades, loading bars) and
   cosmetic randomness (`src/audio/client-random.ts`) stay in the client.

**Four parts per screen.**

| Part | Lives in | Knows | Never knows |
|---|---|---|---|
| **Controller**: state machine, selection, popups, what a click sends | `src/ui/screens/` | the view, hints, queries, commands, client settings | coordinates, art, fonts |
| **View model**: the named values, flags and lists the layout binds to | produced by the controller | display strings (through the text service), enable flags | pixels |
| **Layout**: widgets, positions, art, fonts and colours bound to view-model names and controller actions | `data/layouts/<skin>/<screen>.json` | the widget vocabulary, asset ids, font ids | rules, the view |
| **Widgets and renderer** | `src/ui/widgets/`, `src/ui/input/`, `src/render/ui-draw/` | geometry, input events | game state |

The skin `original` is the only one; another skin binds to the same controllers (D10). Screen parts that cannot be
generic (the tactical viewport, the strategic map, the radar, faces, inventory slots, the item description box, video,
credits) are `custom` widgets whose geometry comes from layout parameters, so a layout can resize them without touching
the controller.

## 3. The game page and the session

**Screens and modals.** `/play` holds one session client, one WebGL2 context, one audio engine, one asset source and
cache, and a `ScreenHost` (`src/ui/screen.ts`): a screen stack under a modal stack. Modals take input first and block
the rest unless they pass unhandled input; the screen under a modal is drawn but not updated, and a modal that freezes
the screen (message boxes, fades) replays the draw items taken when it opened. Tactical, map screen and laptop are
screen changes on one page, so decoded assets survive them. The front-end flow follows the server: a frame that shows
another flow while a game screen is up re-enters the game, so every screen change the server makes takes one path
(`30`). A page that fails to boot shows a plain HTML panel with the reason and Retry, since the game's fonts may not
have arrived; `?screen=testPattern` shows every draw primitive (the golden of `tests/e2e/play.spec.ts`).

**Time while the client shows something modal.** The original pauses game time while a message box, the options or
save screen, help, a popup menu, the pickup menu or the sector inventory is open, at the event that opens it
(`MessageBoxScreen.cc:270-274`, `Options_Screen.cc:169`, `HelpScreen.cc:465-472`). In ja2-node the server owns time:
- client modals call `UiRuntime.pauseGame`; `ModalPause` (`src/app/game/modal-pause.ts`) counts nested ones, switches a
  running real-time driver to manual for the outermost and restores it after the last, only on the same session and
  only while the driver is still manual, so a driver set by someone else meanwhile stays;
- a box opened by an event on the map screen (the update box, the lost sector box) relies on the real-time driver's
  `pauseOn`, which stops on the event's tick (`04`);
- decision prompts freeze the server anyway (D15).

**Connection.** `SessionClient` keeps its session over `src/app/net/session-link.ts`. A closed socket, or a server
silent after a heartbeat ping, makes it dial again with a growing delay and a hello for the same session; requests made
meanwhile fail at once, except `drive`, which only records the wanted driver until the welcome brings back the
server's. A welcome from the same server `instance` (`04`) restores the session and resets the client like a load in
place; another instance or an unknown session ends it as gone, a `closed` message with the server's reason. The flow
shows a `reconnecting` box meanwhile and leaves for the main menu, naming the reason, when the session ends.

**The client's copy of the game.** `SessionClient` keeps the **shown** view, advanced by playback, and the **latest
received** one, which the hints read; both move by the protocol's generic `applyViewFrame`, so every field the server
adds reaches the screens without client work. The stub scenario suites check it as the inverse of `diffPlayerView`
after every dispatch and advance (`ReloadingSession` with `tests/support/view-mirror.ts`). The client also keeps the
message log, the frames not yet played back (which the tactical input lock reads, `30`) and the `welcome` identity.

**Animation frames.** A soldier's `frameDelay` depends on breath, life, agility, terrain, combat and stealth, so the
client cannot compute it: each soldier entry carries the animation state, the logic frame slot, the state's start tick,
the delay and the tick of the next frame, and gameplay markers arrive as events with ticks (`shotFired`,
`meleeStrike`). Fine animation between the 50 ms frames comes from this schedule, not from a smaller frame interval.
`SoldierFrames` (`src/app/world/soldier-frames.ts`) compares the hash of the client's own animation scripts with
`welcome.rules.scripts`:
- **same scripts** (always while the client reads its files from the server, §5): the sprite frame is the
  presentation frame of the predicted slot, equal to the server's;
- **different scripts**: the client walks its own script per state and plays it from the state start, warped piecewise
  between the start and the ticks of the fire markers, holding before a marker not yet received; a muzzle flash still
  coincides with the shot, and nothing flows back from the picture (deviation "Soldier frames with other scripts").

Within a state at a constant delay the slot advances at fixed ticks along the state's walk, so `predictedFrameSlot`
(`src/content/anim/schedule-track.ts`) finds it at any later tick, and the server does not resend a soldier whose
silent animation the client predicts (`keepPredictableFrames`, `04`); `src/server/frame-anchors.test.ts` checks the
prediction against the simulation at every frame tick.

## 4. Cursor hints

Cursor feedback needs answers several times a second (the path and AP cost under the pointer, the chance to hit, drop
targets, ETAs while plotting, enabled menu lines). The original computes them in the UI with the rules' functions;
ja2-node runs the simulation's own hint functions (`src/sim/hints/`) in the browser over the player-knowledge
projection of the view, and the server answers the same kinds over the same projection on its query channel for
agents, as the fallback and for verification. Client and server agree by construction: same code (the engine commit),
same inputs (the rule pack and scripts hashes of `welcome`). Kinds, projection, channel and fairness: `29`; which
screen asks which hint: `30`.

- `ClientKnowledge` (`src/app/hints/`) loads the rule content through `src/app/rules/client-rules.ts`, which hashes the
  pack from the manifest like the server, and the server's own loaders; it is usable only when the engine identity the
  build injects and both hashes equal `welcome`'s. The map host opens it as part of its load; the tactical host after
  its screen has loaded, so the server answers the first hints. Each host opens its own.
- `HintProvider` implements `GameClient`, polled every frame: a request is answered once the same request of its kind
  has been asked for 80 ms (the original's `PATHFINDCOUNTER`, `Utils/Timer_Control.cc:18`), on the latest received
  view, with one projection per view and answers cached per view. It asks the server while the knowledge is
  unusable, and for a hint that reads the loaded sector while its map is still loading (`hintReadsSectorWorld`); the
  map screen's hints need only the strategic knowledge, so its Tactical button does not wait for the server after
  every new view.
- **Shadow mode** (`?shadowHints=1`, on in the e2e flows) also asks the server and compares over the view the client
  holds when the reply arrives. The `src/server/hints-*-stub.test.ts` suites and their `-original` twins compare client
  answers, built by the strict projection from the serialised view alone, with server answers over sampled points.

## 5. Assets

**Rule pack and media.** The simulation reads only the rule pack, which the server builds from its data and binds saves
to (`04`); graphics, sounds, music, videos and fonts are media, which only the client needs. Graphics stay
palette-indexed in every scenario (soldier palettes, shade tables and outline colours need the indices), and ja2-node's
own code decodes STI, PCX, ETRLE, IMA ADPCM, GAP and Smacker, so no browser codec matters.

| Scenario | Rules on the server from | Media on the client from | Status |
|---|---|---|---|
| Stubs only | the stub pack | the server | built |
| The user's data on the server | `JA2_DATA_DIR`, built into the rule pack and cached | the server, by immutable content-hash URLs | built |
| The user's data on both | `JA2_DATA_DIR` | the client's own folder, each file checked against the manifest, a mismatch fetched from the server | not built |
| The user's data only on the client | a pack the client builds and uploads, hash first | the client's own folder | not built |

The seams for the last two exist: the pack is an artifact with a hash; the client reads files through a replaceable
`AssetSource` (a local folder could be read with the DOM-free SLF parser over `Blob.slice`), builds the same rule
content with the same loaders, and warps the animation schedule when its scripts differ (§3). Missing: the local folder
source and its per-file check (the data version must match too, since text lengths time speech), the validated pack
upload, per-session content and per-user pack storage.

**On the client** (`src/app/assets/`). The user's data is about 860 MB and a tactical screen needs about 10 MB of it,
so the client fetches files on demand. `HttpVfsLayer` implements the content layer's `VfsLayer` from the manifest, so
path normalisation, layering and the stub fallback are the same `Vfs` class as on the server; it reads by
`/vfs/@<hash>/<path>`, shares one fetch per file among its readers and aborts it when the last one leaves. A 404 on a
hash URL means the data changed since the manifest (`StaleAssetError`); the `/vfs` helpers then fall back to the plain
URL. `AssetCache` keeps decoded values by content hash and decoder; decoding is cheap, so the persistent layer is the
HTTP cache, not a client store. A screen preloads the assets its layouts reference (`src/ui/layout/references.ts`)
before it enters; every content loader takes a `ReadFile`, so a local source needs no loader change.

**Loading in parallel.** The loaders run independent branches at once (the tactical and map hosts, boot, the front end,
layouts, strings, soldier tables and palettes), so a remote browser pays the HTTP/1.1 limit of six requests at a time
rather than one round trip per file. The tactical screen does not wait for its sound: the director and the ambient join
the running screen, which drops sound events until then.

## 6. Resolution and the canvas

Stracciatella keeps every fixed screen at 640×480 centred at `STD_SCREEN_X/Y` with black around it, widens only the
tactical viewport and centres the tactical bottom panel, whose team slots follow the `squad_size` policy, 6 by default
(`UILayout.cc:55-138`, `:167-176`). ja2-node adopts that model with an integer **UI scale** (`src/ui/resolution.ts`):
- auto scale = the largest integer that keeps 640×480 in the window, or a forced scale from the client setting
  `uiScale` or `?scale=`; the logical size is the window divided by the scale, at least 640×480 (1920×1080 → scale 2,
  logical 960×540, a 960×420 tactical viewport). The "640×480 only" option (`fixed640`) keeps the logical size at
  640×480 on every screen;
- fixed screens are laid out in the `std640` frame; the few full-screen elements (the main menu buttons and copyright,
  message box centring, tooltips) use the logical screen (§8);
- the frame is drawn into a framebuffer at the logical size and copied into a canvas of the same size, which the
  browser scales (`image-rendering: pixelated`) to exactly `logical × scale` device pixels at an offset whole in both
  CSS and device pixels (`alignedOffset`: Chrome and WebKit place a canvas at whole CSS pixels). The GPU writes 4–16
  times fewer pixels than for a device-sized canvas, and no fractional canvas size makes the browser filter the
  picture. When even 640×480 at scale 1 does not fit, the canvas shrinks to fit;
- pointer coordinates go through the inverse transform (`toLogical`), and pointer capture keeps a release outside the
  stage.

The viewport size never reaches the simulation. A sharp-bilinear fit for non-integer scales is not built.

**An unchanged frame is not drawn again.** `GamePage` leaves the canvas as shown when the world's picture number and
the UI's draw items (plain data, compared field by field) equal the last drawn ones at the same resolution, after a
frame that missed no image or font; at least one frame in 500 ms is drawn anyway. A still scene touches neither the GPU
nor the compositor; what remains is the original's own motion (animation frames, animated tiles, glows, blinks, the
radar dot). The world's partial redraws are `05`.

## 7. The widget foundation

`src/ui/input/`, `text/`, `widgets/` and `cursors/` port the original's foundation (`src/sgp/MouseSystem.cc`,
`Button_System.cc`, `Font.cc`, `Cursor_Control.cc`, `Utils/WordWrap.cc`, `Utils/Cursors.cc` and the shared widgets of
`Utils/`: popup boxes, merc text boxes, message boxes, sliders, text fields, progress bars, fades). Every rule is unit
tested with scripted event sequences next to the code, on the stub fonts in CI and the original fonts with
`JA2_DATA_DIR`, and the widget gallery shows each widget. What differs from the original's mechanism, and why:

- **One draw list rebuilt every frame from the retained widgets**, in one order: the screen, the modals, tooltips, the
  diagnostics overlay, the cursor. No dirty rectangles, background rectangles or save buffers; a message box freezes
  the screen under it as draw items, not pixels.
- **Regions are hit-tested again on the next frame after any change**, so a region that appears under a still pointer
  takes effect at once (deviation "Mouse region refresh"). Double clicks and held-button repeats come from raw down and
  up events on the injected clock, never from the browser's `dblclick` or the OS key repeat.
- **The cursor is drawn in software**, last in the draw list, with `cursor: none` on the stage: a CSS cursor can
  neither scale with the canvas nor carry the live text the original prints in it (hit chance, AP cost).
- **Fades** step every 16 ms on the UI clock and multiply the frozen frame once (deviation "Fades"); zooms capture the
  frame into a texture and stretch it in the shader. No pointer warp and no mouse confinement (deviations "Pointer
  warp", "Mouse confinement"); text fields have no editor input types and no IME (deviation "Text input").

**Fonts and text.** `FontSet` (`src/ui/text/fonts.ts`) maps the original's 16 font macros to their STIs; one glyph
table per data version maps a code point to a glyph index for all fonts (`src/content/text/glyph-table.ts`, `31`).
Text colours are 8-bit palette indices resolved through the palette of the font being printed, since the font palettes
differ in a few indices (`src/content/text/font-colors.ts`). `DrawTextToScreen` sets the font, foreground and
background but inherits the shadow colour from earlier calls, resolved through the font current then
(`Utils/WordWrap.cc:126-150`); ja2-node's layouts give every text its shadow, resolved through that text's font.
Measuring and wrapping follow the original's integer arithmetic exactly, because mail and files break into pages by
the measured height. The 33 pictures with baked-in text (`mlg.json`) are chosen by the data version, not the display
language; layouts name the MLG id, never a path (`31`).

**Keyboard.** A key is `event.key` when printable ASCII (lower-cased), else taken from `event.code`, which gives
non-Latin layouts their Latin keys; the keypad goes by `code` unless NumLock is off (`src/ui/input/events.ts`). The
original hard-codes whether each hotkey fires on key-down or key-up and with which exact modifiers; ja2-node keeps both
in hotkey tables per layout and modal (`src/ui/input/hotkeys.ts`), which would also allow remapping. Text fields get
keys first. The page `preventDefault`s every key except with Meta; Ctrl+W, Ctrl+T, Ctrl+N and Ctrl+Tab cannot be
overridden. Alt+Enter on release toggles fullscreen and takes the Keyboard Lock (Chromium), so Esc reaches the game
instead of leaving fullscreen. Scroll Lock's mouse confinement and the Print Screen PNG are not built.

**Draw list and blits.** The draw list (`src/ui/draw-list.ts`) holds images, glyph runs, fills, rectangles, lines,
shades, hatches, clips, captures and snapshots, with the original functions' coordinates. `src/render/ui-draw/` draws
it with one instanced program and a GPU-free planner (`ui-plan.ts`, unit tested) that batches by atlas page, texture,
blend and scissor. Images and glyphs share one R8UI atlas and palette rows, so the original's blit effects (indexed and
mono-shadow text blits, `ShadowRect`, hatches, outlines, shaded palettes) are shader modes; 16-bit pictures (PCX
backgrounds, load screens) are RGB565 textures. Colours stay the palettes' 24-bit values: the original's final RGB565
quantisation of the UI is not reproduced. Diagonal lines use a plain Bresenham walk instead of `LineDraw`'s run-length
slices.

**Quirks of the original the foundation keeps**, pinned by tests in `src/ui/`:

| Quirk | Test |
|---|---|
| Among regions of equal priority the newest wins, and the hit test includes the bottom-right edge | `input/regions.test.ts` |
| A release over no region keeps the press lock and swallows the next click elsewhere | `input/regions.test.ts` |
| `DrawTextToScreen` centres without the +1 of `CenterAlign` and wraps its x like a `UINT16` | `text/text.test.ts` |
| A word split at the line end does not count its overflowing character; text from U+4E00 on breaks one character early | `text/text.test.ts` |
| Ian code 180 colours with 184 whatever its argument | `text/text.test.ts` |
| Money puts the minus after the dollar (`$-1,234`) | `text/text.test.ts` |
| `SetSliderValue` ignores the slider's maximum | `widgets/widgets.test.ts` |
| Tab that finds no other enabled field comes back to the field it left and stops editing there | `widgets/widgets.test.ts` |

## 8. Layouts as data

**Provenance.** `data/layouts/original/<screen>.json` is validated by `src/ui/layout/schema.ts`. Coordinates come from
Stracciatella's constants, so each layout is SFI-SCLA-derived and carries `@derived` and `@src` (the source functions
and lines). Numbers are referenced by name from generated tables: `tools/transcribe/ui-constants.ts` extracts the
`#define`, `static const`/`constexpr` and enum values of each screen's sources into `data/tables/ui-constants/`,
evaluated with `STD_SCREEN_X/Y` = 0 (inside `std640`; the names that contained them are listed in `stdScreen`), and
constants written relative to the tactical panel stored panel-relative. A literal is allowed only where the source has
an inline literal, with the line in `@src`. Layouts never contain original data; on the stubs the same layouts draw
the stub art (§9).

**What the format says** (`model.ts`, `view.ts`, `frames.ts`):
- **Frames**: `std640`, the logical `screen`, the tactical `viewport` and the tactical panel and inventory frames
  centred by the `UILayout` formulas; per-widget `within`, nine anchors, centring on the logical screen, a run-time
  origin for panels that move (the talk panel, help).
- **Numbers**: integers, constant names or integer expressions with C division over them and the screen and repeat
  variables. **Conditions** are a binding, its negation or an equality, never an expression language.
- **Art, text and input**: assets as STI, PCX or MLG id with a stub size, button frame sets, choices by a bound state;
  fonts by macro, text colours as palette indices with the shadow always explicit; text from string keys, bindings,
  EDT fields, formats and money; regions with priority, cursor, tooltip and actions per mouse event; text fields and
  the original's user fields (`AddUserInputField`: Tab stops on them, an action hears the focus come and go) in one Tab
  order by document order; hotkeys with key, phase, modifiers and condition that call an action, give a field the focus,
  or both.
- **Order**: draw order is document order; input goes by priority, then the later widget (newest first, as the
  original's regions).

**The bindings contract.** Each controller exports typed actions and bindings (`src/ui/screens/contracts.ts`).
`src/ui/layout/layouts-contract.test.ts` loads every layout of every skin and checks the schema, the bindings and
actions both ways (or marked `unsupported`), provenance, literals only in debug layouts, an explicit shadow on every
non-debug text, a stub size on every asset, known fonts, cursors and string keys, and every asset, frame and EDT file
on the stub pack; with `JA2_DATA_DIR`, every asset and frame on the original data and the PCX backgrounds at least as
large as the boxes the code sizes by constants. **Layouts are JSON** rather than TypeScript modules so that another
skin can be written without code; it may use other frames and colours and combine, hide or move widgets, but must call
the same actions.

## 9. Stub skin

CI runs on stubs only (`32`), so the stub pack carries what CI needs to render and test every screen on the canvas;
quality is not a goal. Stub art is original work with deterministic bytes, written as **STIs (and PCX where the code
loads a PCX) under the original names**, so layouts reference `(file, frame)` the same way on both data sets and one
decode path serves both. **Sizes come from the layouts**: where the art, not the code, defines a size, the stub
chooses its own and the layout carries the size it needs, so no layout centres a sprite on an original image's
measured size. MLG ids resolve to the base names on the stub data version.

`stubs/ui/skin.ts` writes, for every asset a layout references and the stub pack lacks, an STI with the frames the
layout uses: bevelled rectangles at the declared size, stamped with the file name and frame number, button states
visibly different. Adding a layout adds its stub art, so the layout contract resolves on stubs by construction. Assets
whose content the tests read have generators of their own, each with a decoder round trip in `stubs/build.test.ts`:
cursors (hot spots and animation), faces (blink and lip-sync frames at the offsets of `stubs/profiles.json`), item
pictures, the strategic map board (coloured by traversability, for sector picking and shading), radar maps (from the
stub maps' own tiles), load screens, and the help and laptop texts (`stubs/text/`). The stub media have a size budget
in `stubs/build.test.ts`.

**Deliberate stub gaps.** The stub dealer, repairman and Speck have no dialogue rows, and the stub world has no pointer
tiles: new NPC rows or tile types would change the stub content the recorded stub saves bind to (`32`). So their lines
are silent, Speck talks without subtitles and cursor markers draw only on the original data. The stub tilesets have no
small tiles, so on stubs the overhead map is black under the persons.

## 10. Verification

- **Units and draw lists** (Node): controllers run over fake `GameClient`s on live stub sessions (`tests/support/`:
  `tactical-ui.ts`, `map-ui.ts`, `laptop-ui.ts`, `laptop-sites-ui.ts`, `battle-entry.ts`); draw-list snapshots in
  `__snapshots__/` beside the tests are exact, GPU-free regressions.
- **The hook.** `window.__ja2Ui` (`src/app/game/ui-hook.ts`, extended by the hosts' `*-hook.ts`) reports the screen
  state and offers `capture()` (the logical framebuffer) and `skipPlayback()`. E2e tests click widget centres and
  press keys by `KeyboardEvent.code`; every wait is on hook state, never a fixed timeout. URL switches freeze what a
  test needs frozen: `?drive=manual` the driver, `?pinClock=1` the UI clock, `?holdTime=1` game time on the map
  screen; with `?shadowHints=1` a test fails on any hint that differs from the server's.
- **`pnpm e2e`** (Playwright on stubs, `tests/e2e/`): the main flow (a new game, an A.I.M. hire, the landing battle with
  cursors and the HUD, a route, a save and its load) and one spec per screen. **Goldens on stubs only**: the logical
  framebuffer against PNGs in `tests/e2e/golden/`, the clock pinned. The suite hides help screens by default so they do
  not change other specs' goldens.
- **`pnpm e2e:data`** (`tests/e2e-data/`, opt-in with `JA2_E2E_DATA_DIR`, never in CI) runs the main flow, a tour of
  the screens and the performance measurement on the original data, asserting structure only (widgets, texts, no
  missing image or font, no refused command, no failed read). **No picture of the original data is ever taken**: the
  data fixture replaces `capture()` and `page.screenshot` by functions that throw before any page script runs.
- **`pnpm e2e:browsers`** (`tests/e2e-browsers/presentation.spec.ts`): the main menu in Chromium and Firefox at
  fractional pixel ratios and odd window sizes, with and without the 640×480-only option; a device-pixel screenshot
  must equal the logical capture scaled by whole blocks (§6). Firefox needs a display (`xvfb-run`) and
  `webgl.force-enabled`. Playwright's WebKit is not used: it is a Linux build, not Safari, and needed a test-only
  drawing-buffer mode while blending the last column at fractional ratios, which Safari (whole ratios only) never
  meets.

## 11. Performance targets

| Target | Value | Measured with |
|---|---|---|
| Tactical frame time at 1920×1080, UI scale 2, original data, a busy sector (A9, 12+ soldiers), real time | p95 ≤ 16.7 ms (60 FPS) | a GPU machine: not yet measured |
| Static world per frame (JS) | ≤ 1 ms | the tactical hook's `worldMs` |
| Draw calls, tactical with HUD | ≤ 250 | the tactical hook's `drawCalls` |
| Screen switch tactical ↔ map ↔ laptop, assets cached | ≤ 100 ms | not instrumented |
| First tactical load from a cold HTTP cache (local) | ≤ 2 s including the loading screen | the tactical hook's `loadMs` |
| A cursor hint computed in the browser | ≤ 2 ms p95, path search included | the hint hook's `stats` |
| Server query round trip (local) | ≤ 10 ms p95 while no enemy turn runs; never queued behind an advance | not instrumented |

`tests/e2e/performance.spec.ts` (stubs) and `tests/e2e-data/performance.spec.ts` (A9 at 1920×1080) record the page's
JavaScript time per frame. Headless Chromium without a GPU (SwiftShader, CI) reads every WebGL frame back in software,
so its frame intervals say little about a real machine; JavaScript time per frame is the comparable number. The stubs
probe pins the UI clock, so its still screens have none of the original's own motion and may be drawn only for the
half-second refresh (§6); the draws are counted against the sample's wall time, not its frames, since a slow page shows
fewer frames a second but as many refreshes.

## 12. Limitations and decisions

- **Disconnects** do not pause the game: a real-time driver keeps running on the server until the client is back, since
  the modal pause of §3 cannot reach a server the client has lost.
- **Goldens missing**: the San Mona screen (no stub brothel scenario; `san-mona.test.ts` covers it) and the A.I.M.
  conference (its snow and video run on the UI clock). The main flow hires three of its four mercs through MCP and lets
  the campaign bot fight, so the canvas path covers one hire, the cursors and one shot.
- **Not built**: the cover and line-of-sight display (it needs per-tile cover and sight maps from the simulation, a
  heavy computation), the 3D cursor, touch input, a key remapping UI, the client-side data scenarios (§5) and audio
  transcoding for remote play.
- **The message log is server presentation entries** saved with the session rather than a client-only table: agents
  see them, saves keep them, and one audit pass covers every message (`29`, deviation "Message list").
